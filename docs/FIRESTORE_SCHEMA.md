# Firestore collections (as used by the code)
users(id=Firebase UID: name,email,role,active) · leads(contact fields, stage, stage_history[], owner_id, source, provenance{}, verified_fields[], last_activity_at, next_action, next_action_due, archived, suppressed, import_batch_id) · activities(lead_id,user_id,type,outcome,notes,at,follow_up_due) · tasks(lead_id,owner_id,due_at,status,idem_key) · opportunities · importBatches · enrichmentJobs(items[]) · config/main(stages,outcomes,stale_days) · auditLogs · aiActions.
Queries go through `db.query()` (firebase.py). By design it needs NO composite indexes: it only uses equality-only filters (merged from single-field indexes) and `order_by`+`limit` with no filter (single-field index). Leads/tasks/activities are filtered in the store and sorted/paged in Python over the narrowed set. If you later add a filter AND a different-field `order_by` (e.g. leads where owner_id== order by created_at desc, or true keyset paging of a filtered list), Firestore will return an error containing a link to create that composite index, e.g. leads(owner_id, created_at desc), tasks(owner_id, status, due_at), activities(lead_id, at desc).
Still full-collection reads (fine at small scale, revisit if the data grows): analytics activities/tasks/opportunities in `scoped()`, `find_dupe` (active leads), `agents.py` and `story.py`.
Import rows live in `importBatches/{id}/rows/{chunk}` (about 400 KB per chunk) and are deleted when the import is confirmed. Abandoned uploads leave their rows behind: delete old `importBatches` with status `uploaded` periodically.
Users: first-login accounts are created with `pending: true, active: false` (see FIRST_LOGIN_POLICY / BOOTSTRAP_ADMIN_EMAILS in .env.example).
Notes: `stage_history` is bounded in practice; move to a subcollection if it grows. Firestore Rules are defence in depth only: the Admin SDK bypasses them, so backend checks stay mandatory.
